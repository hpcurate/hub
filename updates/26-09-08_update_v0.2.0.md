### The filled template

**Bump:** minor (`@feature`) — `0.1.0` → `0.2.0`

**Headline:** A companion Vivaldi extension that gates YouTube behind the hub board

**Why:** Stated in the request itself: opening YouTube directly is the problem.
The extension makes the hub the only door in, so a visit starts as a choice of
channel rather than a landing on the home feed. Hugo already runs an extension
that strips recommendations and other YouTube sections; this is the layer above
that — it decides *which channel* he is allowed to be on at all.

**Where:** other — the extension is a new surface across the whole app, not a tab.

**Done when:**

- the hub folder loads in Vivaldi as an unpacked extension, and its board is the extension's own page
- opening YouTube in a tab that did not come from the hub blurs the page and puts the hub board over it
- picking a channel from that board navigates the tab to the channel and stops blurring
- videos of the allowed channel open and play normally, without the overlay flashing over them
- leaving that channel — the home feed, search, another channel — brings the overlay back
- the toolbar popup has an on/off toggle and a pause, and the overlay itself offers a way out
- nothing on a non-YouTube page is ever touched, and a failure anywhere leaves YouTube unblurred rather than blocked

**Don't touch:** not stated. Taken as read that the standalone `index.html` must
keep working from disk exactly as it does now, since that is what v0.1.0
delivered and it is not what this task asked to change.

**Notes** — inferred, because the Todoist fields did not say:

- `tab: new extension` is not one of the tab values in the protocol → treated as
  `other`, which is what a whole new surface is.
- Vivaldi is Chromium, so the extension is Manifest V3, loaded unpacked.
- "turns the webpage into an extension" is read literally: the repo root becomes
  the extension, so one copy of the board serves both the standalone page and
  the extension rather than the app being duplicated.

## What was done

### The repo is the extension — task 1

"Turns the webpage into an extension" is taken literally. `manifest.json` sits
next to `index.html`, so loading this folder unpacked in Vivaldi gives both the
board as an extension page and the guard on YouTube. There is one copy of the
board, not a website and a fork of it inside an extension, which is the only
version of this that stays true a month from now. Opening `index.html` off disk
still works exactly as it did in v0.1.0.

Extension-only files live in `ext/`; only `manifest.json` and `icons/` are new
at the root. The icons are generated by `icons/make-icons.py` — a PNG is a zlib
stream in three chunks, so no dependency and no binary to hand-edit.

### What counts as "inside the channel" — tasks 1 and 2

`ext/scope.js` is the whole of that judgement, and it is deliberately pure: no
chrome APIs, no DOM, no state. The service worker imports it, the content script
lists it first, the board loads it, and the tests evaluate it off disk. One copy
of the rules and four readers.

YouTube spells one channel four ways — `/@handle`, `/channel/UC…`, `/c/name`,
`/user/name` — and there is no way to convert between them without asking
YouTube. So a grant does not normalise; it *collects*. It starts as the one name
the board had, and the channel's own page teaches it the others from that page's
`meta[itemprop="channelId"]` and its canonical link. Only ever from things that
describe the page itself: a channel page is full of links to other channels, and
learning an alias from one of those would unlock exactly what this is for.

### Blocking and unblocking — task 1

`ext/guard.js` runs at `document_start` and applies the veil before YouTube has
painted anything, so an allowed page is unveiled again long before its first
frame and a blocked one is never seen. `<body>` is what blurs, not `<html>` — the
overlay is a sibling of body, so it stays sharp above a blurred page. Anything
playing is paused; a blurred page still talking is the one thing that would make
this feel broken.

The overlay is the board itself, in an iframe of the extension's own page, inside
a shadow root so YouTube's stylesheet cannot reach it. Picking a channel there
sends the grant to the background, waits for it to land, and only then asks the
page to navigate — the picker cannot navigate a youtube.com document itself, and
the guard refuses any message that did not come from the frame it created.

Grants are **per tab**. "Whenever I open YouTube" means a fresh tab, and a grant
that lived globally would mean picking a channel once unlocked every YouTube tab
afterwards.

### Seamless — task 2

Two things do the work.

A video clicked from the channel's own page is cleared *before* the navigation
happens, so its watch page is allowed instantly and the overlay never flashes
over it. Only from a channel page: on a watch page the sidebar is other people's
videos, and clearing whatever was clicked there would quietly unlock the thing
the guard exists to stop.

For a watch page arrived at any other way, the owner cannot be known until the
page says so. Blurring first and asking afterwards would flash the overlay over
every allowed video, so the answer is *pending* — a third state next to allow and
block. The page is unveiled optimistically, the owner is read as it appears, and
the veil comes back only if it turns out to belong to someone else.

### Fault-proof — task 2

The rule the content script is written around: **a failure must leave YouTube
alone.** Every path that could hang ends in an unveil — the background not
answering (1.5s), the owner of a video never appearing (2.5s), the board's iframe
not loading (3s, and the escape bar is outside it), the extension being reloaded
under a live page, and a deadman timer above all of them. The veil's only record
is one class on `<html>`; there is no second flag that could disagree with it.

Three ways out, always present on the overlay and two of them in the popup:
dismiss this tab, pause 15 minutes, turn the guard off. Plus `esc` three times
inside two seconds, which is the one that works when the overlay itself never
came up.

**Decision made on Hugo's behalf:** the guard does not clear a tab's grant when
that tab leaves YouTube and comes back. Doing so needs the `tabs` permission —
read access to the address of every page in the browser — for a case that only
ever re-opens a channel the board already holds. The home feed, search and every
other channel stay blocked either way. The extension asks for `storage` and
YouTube, and nothing else.

**Second decision:** the board off disk and the board inside the extension are
different origins and so keep different channel lists. Rather than add an
import/export nobody asked for, the README carries a one-line console snippet
that moves the two keys across.

### The board learned one thing — tasks 1 and 2

`js/bridge.js` is the only file in the app that knows the extension exists.
`index.html` is three things — a page off disk, the extension's page, and the
picker in the overlay — and the bridge is what tells them apart. Off disk it
declines and the anchor behaves like an anchor; as the extension's page it asks
the background to open a tab that is granted before it loads; as the picker it
unlocks the tab it is sitting in. `js/app.js` gained four lines that ask it.

all passing**:

| `picker.mjs` | 22 | the board in all three lives, and that a refused grant never navigates the tab |

**Not verified:** anything that needs a real browser. No extension was loaded in
Vivaldi from this session, so the actual install, the real blur, the iframe
rendering the board, and YouTube's own markup matching the owner selectors have
not been seen. The selectors in particular are a guess at YouTube's current DOM
made from several known spellings — the fallback if they all miss is to allow,
by design, so the failure mode is a video that slips through rather than a page
that traps.
