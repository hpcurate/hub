## What was done

### The avatar — 1

It had three dials — size, shape, edge — and the shape and the edge were on the
`<img>`, which is the wrong element: the picture is not always there. Both are on
the box now, so the stand-in for a missing picture is the same shape, size and
edge as the thing it stands in for, rather than the board being two boards.

Six dials, in a section of their own in the card editor:

| | |
| --- | --- |
| **size** | 20–96px, up from 72 |
| **shape** | circle · rounded · squircle · square · **hexagon** |
| **edge** | hairline · none · accent · **ring** — a ring stands off the picture with the card's own ground between, which is what makes it read as a ring and not a thick border |
| **fit** | cover crops the picture, contain fits the whole of it in — which is what a wordmark avatar wants and a face does not |
| **colour** | full · mono · **hover** (grey until you point at it) · **tint** (the picture's light, the category's hue) |
| **fallback** | **initial** · icon · ghost · none |

The hexagon is a `clip-path` and therefore takes no border — a border follows the
box and not the clip, and half of one is worse than none.

**The fallback is the one that earns its place hardest.** Off disk there are
never any avatars, because a `file://` page cannot fetch youtube.com and never
will, so half of HUB had an empty slot on every card. Now it draws the channel's
initial — with the handle's `@` dropped, because that is part of the URL and not
of the name — or the category's icon, or a silhouette, in the category's own
colour. A board with no pictures at all still reads as a coloured board.

And a seventh, which is a different *kind* of display rather than another dial on
the same one: **the wash**. The same avatar again, huge and faint, as the card's
own ground, masked on the diagonal so it is strongest in the corner the picture
already sits in and gone before it reaches the text. Off by default, and a range
rather than a switch, because the line between a texture and a poster you cannot
read the name on is a number and it is not the same number for every board.

### The features — 2

Five, each of them something the board could nearly do already:

- **Sort by newest upload.** HUB has known every channel's latest video since
  v0.5.0 and could not be ordered by it, which is the one order a board of
  channels is really asked for: what is new. Channels with nothing known sort to
  the end rather than to 1970.
- **A "new" chip.** Not a category — a question asked across all of them: only
  the channels that have posted since you last looked. It is on the bar only
  when the answer is yes, and it says how many.
- **The count in the tab's title.** `HUB · 4 new`. What makes a board worth
  leaving open in a pinned tab, or installed, is being able to answer that
  without opening it. A switch, for anyone who wants their tab to say HUB.
- **Pinned channels.** Pinned in a channel's edit pane, written through
  immediately rather than held until save — pinning is something you do to a
  channel that exists, not a field of one. A pin is an **exception to whichever
  sort is on**, not a sort of its own: the four channels actually opened sit at
  the front whatever the board is ordered by. Marked with a badge that is only
  ever on the pinned ones, which is why it can be on by default and cost the
  rest of the board nothing. Same argument as a favourite category, one level
  down.
- **`r`.** Opens one at random from whatever is on screen — from the filtered
  board, because the filter is already half of the choice. A board is a list of
  things worth watching and the hardest question it asks is which one.

### The web app — 3

`app.webmanifest`, `sw.js`, and twenty lines in `js/webapp.js`. Served over https
HUB installs: its own window, its own icon, and it opens with no network at all.

**Nothing in the board knows any of this is happening**, which was the condition
attached to the request. `js/app.js` does not mention service workers; the store
is the same store, the data is the same data, and the only visible addition is
one row in settings.

**It runs nowhere it does not belong.** Off disk `file://` has no origin to scope
a worker to. Inside the extension there is a service worker already — the
guard's — and a second one on top of that is a way to break the guard for no
gain. `webapp.js` checks the protocol and `chrome.runtime.id` before it registers
anything, and where the answer is no, `HubApp.can` is false, the settings row is
not built, and the board is exactly what it was.

**The strategy is network first**, deliberately. A cache-first shell is faster on
the second load and is how you ship a board that quietly keeps showing last
week's code. HUB is a dozen small files; being wrong about which version is
running is a much worse failure than a few milliseconds.

With one exception, which the first honest test found and which is written down
in `sw.js` next to the code: with the network gone, network-first means every
file on the page waits for its own connection to fail before the cache is asked.
A cold offline start took about five seconds. `navigator.onLine === false` now
short-circuits to the cache — a poor answer to "can I reach this server", a
completely reliable one to "is there any network at all", which is the only
question being asked. **The same load then took 201ms.**

Fonts are cached the other way round — cache first, forever — because they are
large, immutable and on someone else's server. Channel avatars are deliberately
*not* cached: they are Google's own CDN with its own rules, and a copy of ours
would outlive the one the browser keeps.

`icons/make-icons.py` grew the two sizes a manifest wants plus a **maskable**
one, which is drawn full bleed with square corners because the platform crops it
to its own shape and the rounded ground that suits a browser tab would have its
corners cut off.

## Verification

`cd test && npm test` — 524 checks across the five files, all passing, 52 of them
new.

The harness covers: a channel with no picture keeping its avatar box and drawing
its initial, the fallback switching to the icon and to nothing (and the box then
leaving the card while a channel *with* a picture keeps its own), the five
shapes, the ring, contain, hover, the wash setting `--wash` and carrying the
channel's own picture — and not carrying one for a channel that has none; sort
by newest upload with the unknowns at the end; the new chip counting and
filtering to exactly the cards with a dot; pinning from the edit pane, written
through immediately, first under two different sorts, switchable off; the title
counting and not counting; `r` opening exactly one card, and nothing at all on an
empty board. The web app is checked the way the `[hidden]` rule is — as facts
about the repo: the manifest parses, every icon it names exists, one is maskable,
the worker precaches every file the board is made of, and the registration is in
`webapp.js` and not in `app.js`.

The rest was checked in a real browser, because jsdom neither lays out, paints,
nor has a service worker. Headless Chrome driven over CDP, against a seeded board
with two channels that have no picture:

- the worker registers, activates, and precaches 15 entries plus 3 fonts;
- with the network **emulated off**, the board loads from cache in **201ms**
  with all six cards and the right title — this is what caught the network-first
  problem, and then confirmed the fix;
- `beforeinstallprompt` fires and the settings row shows a real install button;
- the hexagon, the 56px size and the wash all render, and the fallback initials
  are hexagons too — which is the whole point of the shape being on the box.
