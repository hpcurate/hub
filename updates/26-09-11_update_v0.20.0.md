## What was done

### The video page carries two buttons now, not one

Adding a channel meant going to its page first. The moment you decide you want
more of someone is a video of theirs, so **+ add channel** now sits beside
**+ queue** on every video page, and the two say the two different things a
video is worth keeping for: the video, and whoever made it.

The injected button was one button with its own shadow root, positioned by
centring itself — two of those would have been one button underneath another.
So the host now holds a **row**, and the row is the thing that is positioned.
Buttons go into it by key, one at a time, which matters because the two arrive
at different moments: the queue button knows everything it needs from the url,
while the add button has to read who owns the video and then ask the board about
them. Appending the second into a row that is already up is what keeps the first
from being rebuilt underneath a click. (`ext/guard.js`, `ext/add.css`)

The inline case — the button sitting in a channel page's own action row beside
Subscribe — moved entirely onto the host's `.inline` class, which is added only
when that row is actually found. A button that is still floating therefore keeps
the floating shape rather than being built as an inline one and left stranded.

### It knows before you click

*make it know if you have already added a channel.* The button asks the board
one question the moment it mounts — a new `addInfo` message — and comes back
either **+ add channel** or a quiet **on the board**. The same answer used to
cost a click and a record that already existed.

"Already" is the board's own rule about what counts as the same account twice,
not a url comparison: four spellings on YouTube, one on Instagram. That rule was
written inside `addChannel`; it is now `heldBy`, which both the filing and the
asking read, because two copies of it would eventually disagree.
(`ext/background.js`)

### A second menu for the category

*have a second menu appear where you can chose the category.* The click opens
the board's categories under the button — favourites first, when the board says
so, which is the order every list you pick a category from already uses — each
with its own colour, and **no category** at the end. Picking one files the
channel there in a single write.

The category id is checked against the board's own list in the worker before it
is written. A content script is not the authority on what categories exist, and
an id that names nothing would file a channel somewhere it could never be found
again. An unknown id, or the other board's, files it uncategorised.

With no categories on the board there is nothing to choose between, so the click
is the whole action and no menu opens.

A click anywhere else closes the menu. **Escape deliberately does not** — three
escapes inside two seconds is the guard's own hatch out of a stuck page, and a
menu that quietly ate the first one would make that hatch unreliable on exactly
the pages it exists for. One page-level listener does the closing rather than
one per button: a YouTube session is one document for hours, and a listener left
behind by every button ever mounted is a leak with nothing to end it.

### The switch

*this should be a setting you can enable/disable.* **an + add channel button on
video pages**, in settings → youtube, directly under the queue button's own
switch. Default on. Off returns a video page to exactly the one button it had.

### The channel's name

On a watch page the document's title is the *video*, so the existing
`channelTitle()` would have filed "A good video" as a channel name. The owner's
name is read from the places YouTube spells it on a watch page, and when none of
them is there the record falls back to the name taken from the url — which is
what `makeChannel` has always done.

## Verification

`cd hub/test && npm test` — 787 checks, 0 failures, across the eight modules.

- **`test/guard.mjs`** (69, up from 53): a video page carries both buttons in
  order; the board is asked about the video's channel rather than the page; the
  menu lists every category plus *no category*; picking one sends the channel
  url, the category id and the channel's name rather than the video's title; the
  button then says *added*; a channel already on the board says so before it is
  clicked and does nothing when it is; with no categories one click files it; a
  board that cannot answer leaves the queue button alone and adds nothing; the
  setting off returns the page to one button; a channel page still gets neither.
  Every pre-existing guard check still passes unchanged.
- **`test/background.mjs`** (20, new): the service worker had no tests at all,
  which is the wrong place for that gap — it is the only code that can put a
  record on the board the board never saw. It runs in `node:vm` with a fake
  `chrome.storage` behind it, and is checked against storage rather than against
  its own reply: the categories come back in pick order for the right platform,
  a channel is filed under the category that was picked, an id that names
  nothing or belongs to the other board files it uncategorised, the same channel
  spelled another way reads as already on the board, and a url that names no
  channel is filed nowhere. Added to `npm test`.

**Not verified:** anything visual, and anything that depends on YouTube's own
markup. The row of two buttons, the menu under them and the colours in it were
not seen in a browser — jsdom establishes nothing about layout — and the
selectors that read the owner's *name* off a watch page are, like every other
selector in `ext/`, a guess at a page that changes. The tests prove the button
does the right thing with what it reads; they cannot prove it reads the name off
today's YouTube.
