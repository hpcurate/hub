## What was done

A channel's home page is a trailer and three shelves you have mostly seen. The
videos tab is the thing that was actually clicked for, so that is where a card
lands now.

### The rule

`HubScope.onTab(url, tab)`, in `ext/scope.js` — the pure file the worker, the
content script, the board and the tests all read. It keeps the **root of the URL
exactly as it was written** rather than rebuilding it from the scope: a handle
URL stays a handle URL, `/channel/UC…` stays `/channel/UC…`, and a board that
stored `youtube.com/@x` without the `www` still goes to `youtube.com/@x/videos`.
A tab **replaces** whatever subpage the URL was on rather than stacking on top of
it, a URL that names no channel is handed back untouched, and a tab that is not
one of YouTube's is refused rather than appended — so nothing can be turned into
a path by a bad setting.

It is in the scope rules and not in the board because the guard's answer depends
on it being true that a tab of a channel *is* that channel. It is: `fromPath`
reads the first path segment only, so `/@x/videos` parses to the same scope as
`/@x` and the guard lets it through on the grant the channel already got. There
was nothing to teach the guard, and the tests say so directly.

### The two ends that use it

- **The anchor.** `hit.href` is `openUrl(ch)` now. The card is still a real link
  showing a real URL on hover, off disk as much as in the extension.
- **The bridge.** `HubBridge.open(ch, { url })` takes where to land. The
  **grant is still read from `ch.url`**, because a grant is a channel and not a
  page — where the tab lands is the board's choice and never the guard's. That
  holds on all three paths: a new tab, this tab, and a tab the guard sent to the
  board.

Nothing else moved. The stored URL is untouched, so the scope, the queue's
matching, the feed lookup and the "+ add" button all still see the channel they
always saw. Opening a videos tab counts as opening the channel, exactly as
before.

### The setting

`openTab`, in the **board** section: `videos` or `home`, videos by default.
`onTab` already knows four more of YouTube's tabs — streams, shorts, playlists,
podcasts — so if one of them is ever wanted it is a word in an array, not a
change.

## Verification

`cd test && npm test` — 472 checks across the five files, all passing.

`scope.mjs` gained fourteen, on the rule alone: each of the four URL shapes, the
host being kept as written, a tab replacing a subpage, asking for the tab it is
already on, `home` and the empty string both meaning the URL itself, a tab that
is not one being refused, a non-channel URL and a non-URL both surviving intact
— and the two that matter most, that a videos tab is inside the grant its channel
got and that another channel's videos tab still is not.

`harness.mjs` checks the card's href, that the stored URL is not touched by it,
the setting flipping to `home` and back, that the choice is remembered, and that
opening a videos tab still counts as an open. `bridge.mjs` checks the URL in the
`openInTab` and `unlock` messages while the scope in them stays the channel.

Checked in a real browser too, headless Chrome over a board seeded with all four
URL shapes: `@handle`, `/c/name`, `/channel/UC…`, and one stored without `www`.
All four land on `/videos` with their own host intact, and the setting row draws
in the board section with `videos` selected.
